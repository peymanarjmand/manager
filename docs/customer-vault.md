# مشتریان و خزانهٔ مشترک

## استفاده

از خانه، «مشتریان» یا «مدیر رمز عبور» را باز کنید. در نخستین ورود رمز مستقل
خزانه (حداقل ۱۲ نویسه) بسازید و کلید بازیابی را خارج از برنامه ذخیره کنید.
دریافت کلید باید تأیید شود. رمز یا کلید را در گفت‌وگو با عامل وارد نکنید.

برنامه پیش از فعال‌کردن بخش‌ها، مدیر رمز فعلی را در مرورگر صاحب حساب بررسی
می‌کند. اصل JSON، نسخهٔ تبدیل‌شده و تصاویر در بکاپ رمز‌شده قرار می‌گیرند؛
بازگشایی داده و تطبیق SHA-256 تصاویر آزموده می‌شود. بکاپ را دانلود و ذخیرهٔ آن
را تأیید کنید، سپس انتقال را نهایی کنید. قطع ارتباط یا تغییر هم‌زمان داده،
اصل را با اطلاعات خالی جایگزین نمی‌کند. شناسهٔ ورودی‌های موجود حفظ می‌شود.

اگر تصویر قدیمی قالب پشتیبانی‌نشده داشته باشد، انتقال متوقف و اصل حفظ می‌شود.
فایل قدیمی با مرجع یا مالکیت مبهم حذف نمی‌شود. باکت مشترک قدیمی برای اثبات
انحصاری‌بودن مرجع کافی نیست، بنابراین این نسخه فایل قدیمی را پاک نمی‌کند.

پروندهٔ مشتری پنج قسمت دارد: مشخصات، پروژه‌ها، مالی، حساب‌ها و سرویس‌ها،
مدارک و یادداشت‌ها. نام و نام خانوادگی و حداقل یک موبایل یا ایمیل معتبر لازم
است. تاریخ تولد اختیاری است؛ تاریخ شمسی را مستقیم وارد کنید، بدون محدودیت سن.
پس از ذخیرهٔ هر رکورد، تصاویرش را از جزئیات همان رکورد اضافه کنید. روی کارت
ملی، پشت آن و تصاویر تکمیلی در مشخصات جای جداگانه دارند.

از هر سرویس چند رکورد و برای هر مشتری چند پروژه ممکن است. رکورد سرویس را
می‌توان به چند پروژه متصل کرد. انتخاب روش ورود Supabase و Netlify، فیلدهای
ورود را تغییر می‌دهد؛ مقادیر قبلی پاک نمی‌شوند. انواع سفارشی، کدهای بازیابی
با علامت استفاده‌شده و کپی مستقل وجود دارند. کپی کد، آن را استفاده‌شده نمی‌کند.

## دفتر مالی

تمام مبالغ عدد صحیح تومانی هستند و با `BigInt` محاسبه می‌شوند. هر مشتری یک
مانده دارد. مبلغ توافق‌شدهٔ پروژه و هزینهٔ پیشنهادی تمدید، طلب ایجاد نمی‌کنند.

| نوع ثبت | علامت در مانده |
| --- | --- |
| هزینه برای مشتری یا حق‌الزحمه | مثبت |
| بدهی من یا دریافت از مشتری، شامل پیش‌پرداخت | منفی |
| پرداخت یا بازپرداخت به مشتری | مثبت |
| اول دوره | بر اساس جهت انتخاب‌شده |

مثبت یعنی مشتری بدهکار، منفی یعنی مشتری بستانکار و صفر یعنی تسویه. پروژه
فقط ارتباط هزینه را مشخص می‌کند. دریافت عمومی به تقسیم بین پروژه‌ها نیاز
ندارد. مبلغ ۵ میلیون هزینه و ۲ میلیون دریافت، ماندهٔ ۳ میلیون طلب می‌سازد؛
با ۴ میلیون دریافت دیگر، مشتری ۱ میلیون بستانکار می‌شود.

ویرایش نسخهٔ قبلی را در تاریخچه نگه می‌دارد. ابطال، ثبت را از جمع خارج می‌کند
و سابقه باقی می‌ماند. بایگانی مشتری یا پروژه هیچ سابقه یا تصویری را حذف نمی‌کند.
بخش مالی مشتریان به حسابدار شخصی و دفترتلفن چیزی اضافه نمی‌کند.

تاریخ‌ها شمسی و ساعت‌ها با `Asia/Tehran` نمایش داده می‌شوند. تولد و تمدید به
صورت تاریخِ بدون ساعت، رخداد مالی به صورت زمان ISO ذخیره می‌شود. تبدیل ساعت
با منطقهٔ زمانی ایران، شامل تاریخ‌های قدیمی دارای ساعت تابستانی، آزموده شده است.

## ذخیره‌سازی و امنیت

- مشخصات، مبالغ، یادداشت‌ها، رمزها، نام فایل و تصاویر پیش از ارسال رمز می‌شوند.
- کلید تصادفی AES-256-GCM برای هر کاربر؛ محافظ رمز با PBKDF2-SHA-256، نمک ۱۶
  بایتی و ۶۰۰هزار تکرار. محافظ بازیابی مستقل با کلید تصادفی ۲۵۶ بیتی و HKDF.
- قالب `EncryptedEnvelope` نسخهٔ ۱، IV تازهٔ ۱۲ بایتی و برچسب صحت ۱۲۸ بیتی؛
  AAD به کاربر، شناسهٔ کلید، جدول، رکورد و نسخه متصل است.
- رمز، کلید بازشده و اطلاعات فقط در RAM هستند. هیچ persist، localStorage،
  IndexedDB، outbox یا کش سرویس‌ورکر برای این دو بخش استفاده نمی‌شود.
- درخواست‌ها `cache: no-store` دارند؛ سرویس‌ورکر تولید برای Supabase NetworkOnly است.
- قفل دستی، خروج و pagehide کلید و storeها را پاک می‌کنند. پس از ۱۰ دقیقه
  بی‌کاری، همچنین هنگام بازگشت از پس‌زمینه، زمان بررسی می‌شود. قطع اینترنت
  مانع ذخیره است؛ پیش‌نویس تا زمان قفل یا بسته‌شدن جلسه در حافظه می‌ماند.
- کپی محرمانه پس از ۲۵ ثانیه یا قفل، در حد اجازهٔ مرورگر و فقط اگر محتوای
  کلیپ‌بورد همان مقدار باشد پاک می‌شود. مقدار جدید کاربر پاک نمی‌شود.
- تمام جدول‌ها RLS مالکیت و GRANT مشخص دارند. کلیدهای خارجی مرکب، مالکیت
  مشتری/پروژه/حساب را کنترل می‌کنند. کاربر دوم و ناشناس آزموده شده‌اند.
- مدیر رمز قدیمی پس از مهاجرت نمی‌تواند متن خام بنویسد یا ردیف رمز‌شده را
  حذف کند. نشانگر مهاجرت و تاریخچه مجوز نوشتن مستقیم برای کاربر ندارند.
- پیاده‌سازی‌های دارای دسترسی ویژه در `private` هستند؛ سه RPC عمومی با
  `SECURITY INVOKER` و فقط برای `authenticated` عرضه شده‌اند. بررسی مالکیت
  داخل پیاده‌سازی خصوصی نیز برقرار است؛ private نباید در Data API expose شود.
- ذخیره با کنترل revision و تأیید سرور انجام می‌شود. پس از پاسخ نامطمئن،
  رکورد با شناسهٔ ثابت دریافت و تطبیق می‌شود تا ثبت مالی تکراری ایجاد نشود.

جست‌وجو فقط در دادهٔ بازشدهٔ حافظه است؛ رمز، توکن، کلید و یادداشت محرمانه وارد
جست‌وجوی عمومی حساب‌ها نمی‌شود. محرمانه‌ها ابتدا پوشیده‌اند. تولید TOTP در این
نسخه نیست؛ اطلاعات و QR و کدهای بازیابی قابل نگهداری‌اند.

## تصاویر و بکاپ

JPG، PNG و WebP تا ۲۰ مگابایت پذیرفته می‌شوند. امضای فایل و در مرورگر امکان
بازشدن آن بررسی می‌شود. اصل بایت‌ها بدون فشرده‌سازی مخرب نگهداری می‌شود.
تعداد محدودیت مصنوعی ندارد و تابع ظرفیت Storage است. مسیر باکت `lm-vault`
از شناسهٔ کاربر و UUID تشکیل می‌شود؛ هیچ نام شخصی در مسیر نیست.

تصویر ابتدا pending است. پس از بارگذاری، فایل رمز‌شده دوباره دریافت، باز و
با اصل تطبیق می‌شود؛ سپس ready می‌شود. اگر پاسخ بارگذاری گم شود ولی فایل سالم
باشد، دریافت دوباره آن را تشخیص می‌دهد. بارگذاری ناقص دکمهٔ بررسی و تکمیل دارد.
نمایش و دانلود با Blob حافظه انجام می‌شود؛ Object URL هنگام قفل یا خروج از
نمایش آزاد می‌شود. اشتراک فایل در صورت پشتیبانی مرورگر ارائه می‌شود.
پیش‌نمایش تصاویر نزدیک محدودهٔ دید دریافت می‌شود تا گالری بزرگ، همهٔ اصل‌ها
را هم‌زمان وارد حافظه نکند. فایل رمز‌شده با درخواست کامل `Range: bytes=0-`
دریافت و اندازه و checksum بررسی می‌شود؛ این مسیر در آزمون واقعی مرورگر
از تبدیل پاسخ binary به دانلود بیرونی و پاسخ خالی جلوگیری کرد.

«امنیت و بکاپ» بکاپ ZIP شامل manifest رمز‌شده، داده، تاریخچه و تصاویر رمز‌شده
می‌سازد. رمز/کلید بازشده در بکاپ نیست. قبل از تحویل فایل، بازگشایی رکوردها و
تصاویر آزموده می‌شود. فایل را می‌توان برای آزمون و افزودن موارد مفقود وارد کرد.
رکورد متفاوت موجود خودکار بازنویسی نمی‌شود؛ بازیابی ناقص قابل ادامه است.
برای خزانهٔ مفقود، همان حساب با رمز یا کلید بازیابی بکاپ لازم است؛ بکاپ متعلق
به شناسهٔ کاربر اصلی است. بکاپ قدیمی را با رمز/کلید معتبر خودش نگه دارید.
خروجی عمومی JSON تنظیمات، مشتریان و مدیر رمز را شامل نمی‌شود.

## ساختار و انتشار

مهاجرت‌ها به ترتیب:

1. `20261027214208_customer_vault.sql`: نه جدول، باکت خصوصی، RLS، GRANT، نسخه
   و محافظ مدیر رمز. هیچ مقدار قدیمی را بازنویسی نمی‌کند.
2. `20261027221932_vault_rpc_boundaries.sql`: انتقال پیاده‌سازی ویژه به private
   و ساخت ورودی عمومی با SECURITY INVOKER؛ امضای API ثابت است.
3. `20261027225008_vault_relationship_indexes.sql`: ایندکس پوشاننده برای هر دو
   رابطهٔ مالکیت در حساب مشترک بین پروژه‌ها، بدون تغییر ردیف یا مجوز.

MCP پروژهٔ `hzloraflhftrxcokbvkv` فقط‌خواندنی باقی مانده است. SQL تولید از
SQL Editor اجرا می‌شود؛ reset و fixture و آزمون نوشتن فقط روی Docker محلی‌اند.
مخزن baseline کامل ۳۴ جدول قبلی را ندارد؛ fixture تست، جایگزین schema تولید نیست.
مرجع کنترل‌ها: `supabase/verify-data-api-access.sql` و `verify-vault-security.sql`.

## آزمون‌های تکرارپذیر

Node 20+، Docker و Chrome لازم‌اند. فقط برای محیط محلی:

```sh
npx supabase start
npx supabase migration up --local
npm run test:vault:prepare
npm test
npm run test:vault:local
npm run test:e2e
npm run typecheck
npm run build
```

اسکریپت prepare فقط localhost را می‌پذیرد؛ اطلاعات اتصال محلی را در پوشهٔ
موقت سیستم خارج از ریشهٔ وب می‌نویسد. کلید service-role محلی وارد frontend
نمی‌شود. fixtureها کاربر و اطلاعات ساختگی‌اند. تست بازیابی فقط در کانتینر
`supabase_db_myapp` و برای شناسهٔ کاربر آزمایشی، حذف تصادفی را شبیه‌سازی می‌کند.
هیچ‌یک از این تست‌ها را به دیتابیس remote متصل نکنید.

نتیجهٔ اجرای این نسخه: ۵۷ تست عادی، ۸ تست یکپارچهٔ دیتابیس و ۲ تست Chrome
با نمای موبایل موفق؛ TypeScript و build موفق؛ lint بدون خطا و با ۵۹ هشدار
در کدهای پیشین. نمای Pixel 7 شبیه‌سازی می‌شود؛ ساعت دستگاه آزمون لس‌آنجلس
است تا مستقل‌بودن نمایش ساعت ایران نیز بررسی شود.

پوشش: محاسبهٔ دقیق و ابطال، تاریخ و ساعت مستقل از دستگاه، رمز و بازیابی
اشتباه، دست‌کاری ciphertext، AAD، دسترسی دو کاربر و ناشناس، لینک پروژه‌ها،
قطع انتقال تصویر، اجرای دوبارهٔ مهاجرت، تعارض، پاسخ گم‌شده پس از ثبت، بیش از
هزار یادداشت و هزار ثبت مالی، بکاپ و بازیابی واقعی، فرم و تصویر و دانلود
موبایل و قفل ۱۰ دقیقه‌ای. تست عادی پروژه به دیتابیس نیاز ندارد.
