# آمادگی Data API برای ۳۰ اکتبر ۲۰۲۶

پروژه: `hzloraflhftrxcokbvkv` (manager). بررسی تولید در ۲۷ اکتبر ۲۰۲۶ انجام شد.

## پرداخت چندمرحله‌ای اقساط — ۲۸ اکتبر ۲۰۲۶

فایل `migrations/20261028115944_installment_receipt_history.sql` پس از آزمون
روی Docker محلی، از SQL Editor همین پروژه اجرا شد. SHA-256:
`46C791C5D869E7327B1AEE1F8248223FB581EE0B33C2C13C87396343DB70E1D2`.

تغییر افزایشی است: ستون JSONB به نام `receipt_history` با پیش‌فرض آرایهٔ خالی
به جدول موجود `installment_payments` اضافه شد. دو RPC با SECURITY INVOKER و
مجوز اجرای مشخص برای authenticated، ثبت و ابطال مرحله را با قفل همان ردیف
انجام می‌دهند. trigger از حذف/بازنویسی سوابق و پرداخت بیش از مانده جلوگیری
می‌کند. پرداخت‌های کامل قدیمی که تاریخچه ندارند، همان وضعیت و تاریخ قبلی را دارند.
جدول تازه‌ای ساخته نشده و grants یا سیاست‌های مالکیت موجود تغییر نکرده‌اند.

پیش و پس از اجرا، `verify-data-api-access.sql` برای هر ۴۳ جدول OK بود؛ پنج
کنترل `verify-installment-history.sql` نیز true شدند. تعداد ۵۴۱ ردیف و اثرانگشت
تمام ستون‌های قدیمی قبل و بعد کاملاً یکسان بود. هشدار جدیدی در Security Advisor
دیده نشد؛ دو هشدار Auth ثبت‌شدهٔ قبلی باقی‌اند.
[تصویر کنترل تولید](../docs/screenshots/installment-history-production.png).

این migration نیز از SQL Editor اجرا شده است؛ پیش از db push بعدی، تاریخچهٔ
CLI باید با فایل‌های واقعاً اجراشده تطبیق داده شود. برای محیط تازه، baseline
معتبر جدول‌های قدیمی باید پیش از migrationها وجود داشته باشد؛ fixtureهای زیر
`supabase/tests` فقط برای محیط محلی‌اند. [راهنمای ورودی مبلغ و اقساط](../docs/money-and-installments.md).

## وضعیت فعلی پس از افزودن خزانه و مشتریان

سه migration بررسی‌شده از SQL Editor تولید اجرا شدند؛ اتصال MCP همچنان فقط‌خواندنی است:

- `migrations/20261027214208_customer_vault.sql`، SHA-256:
  `06DCE0B5E1A27541172A5FBFDAB15AB3030CADE062DCCB9A95EFAB19374B866D`
- `migrations/20261027221932_vault_rpc_boundaries.sql`، SHA-256:
  `104F08882CC4CFA9E7C1ACA013AD17B3B4055B3EBA6AAAF18A321E659FABCC4A`
- `migrations/20261027225008_vault_relationship_indexes.sql`، SHA-256:
  `A94CD18CA2DD150072CDA7880B92D4E981668A62E5166E73CBAE54465D805347`

این اجراها افزایشی‌اند: نه جدول متعلق به کاربر و باکت خصوصی `lm-vault`،
افزودن revision و encryption_version به جدول مدیر رمز، و محافظ‌های نوشتن.
مقادیر قبلی بازنویسی یا حذف نشدند؛ رکورد چینش قدیمی kv_store دست‌نخورده است.
انتقال رمزهای واقعی فقط در مرورگر صاحب حساب، پس از ساخت خزانه، آزمون بکاپ
و تأیید ذخیرهٔ آن انجام می‌شود. عامل رمز یا کلید بازیابی کاربر را دریافت نمی‌کند.

کنترل دسترسی اکنون ۴۳ جدول را با نتیجهٔ `OK` تأیید می‌کند. مجوزهای بخش جدید
عمداً محدودترند: DELETE برای داده‌های مشتری، مالی و تاریخچه به نقش کاربر
داده نشده؛ user_vaults مجوز ستونی دارد. رکورد مالی با ابطال حفظ می‌شود.
هفت کنترل `verify-vault-security.sql` نیز همگی true بودند: RLS نه جدول، سه
RPC عمومی SECURITY INVOKER، اجرای فقط authenticated، محافظ نشانگر انتقال،
باکت خصوصی، مرز مالکیت Storage و ایندکس روابط. [تصویر کنترل تولید](../docs/screenshots/vault-production-security.png).

Security Advisor پس از انتقال پیاده‌سازی توابع ویژه به private، هشدار جدید
دیتابیسی ندارد. دو هشدار Auth قبلی همچنان وجود دارند و تنظیمات Auth تغییر نکرده‌اند:
[Leaked Password Protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)
و [MFA](https://supabase.com/docs/guides/auth/auth-mfa).

مهاجرت‌ها روی Docker محلی با انتشار خودکار خاموش بازپخش شدند. تست دو کاربر،
تصویر، تعارض، شکست اجباری، جلوگیری از نسخهٔ قدیمی، بیش از هزار ثبت مالی و
بکاپ/بازیابی واقعی در محیط جداگانه اجرا می‌شود. fixture و reset تولید مجاز نیست.
اجرای دستی SQL Editor به‌تنهایی تاریخچهٔ CLI تولید را ثبت نمی‌کند؛ پیش از
استفادهٔ بعدی از db push، تطبیق تاریخچه و hash فایل‌ها لازم است و این فایل‌ها
نباید کورکورانه دوباره روی تولید اجرا شوند. [راهنمای قابلیت و تست](../docs/customer-vault.md).

## نتیجهٔ بررسی اولیهٔ تولید، پیش از افزودن خزانه

- هر ۳۴ جدول `public` وجود دارد، RLS فعال دارد و سیاست مالکیت کاربر دارد.
- هر دو نقش `authenticated` و `service_role` برای هر ۳۴ جدول مجوزهای
  `SELECT, INSERT, UPDATE, DELETE` و دسترسی `USAGE` به schema دارند.
- مجوزهای قبلی `anon` نیز وجود دارند؛ سیاست‌های مالکیت با `auth.uid()`
  دسترسی به ردیف‌ها را محدود می‌کنند. برای این بررسی هیچ مجوزی اضافه یا حذف نشد.
- در `public` هیچ view یا sequence وجود ندارد. داشبورد هیچ تابع قابل عرضه‌ای
  برای Data API نشان نمی‌دهد.
- schemaهای در معرض Data API عبارت‌اند از `public` و `graphql_public`.
  اسکیمای `backup_20260614` در معرض API نیست. داشبورد ۳۴ جدول از ۶۸ جدول را
  قابل دسترسی نشان می‌دهد؛ جدول‌های بکاپ نباید عمومی شوند.
- گزینهٔ انتشار خودکار جدول جدید فعلاً روشن است. به آن وابسته نباشید؛
  تغییر Supabase فقط پیش‌فرض اشیای آینده را تغییر می‌دهد و مجوزهای موجود باقی می‌مانند.
- کوئری نهایی همین مخزن روی تولید اجرا شد: ۳۴ ردیف، همگی `OK` و بدون مجوز
  مفقود. ۳۸ سیاست RLS نیز بازبینی شد؛ شرط‌ها مالکیت کاربر یا مالکیت خودروی والد را بررسی می‌کنند.
- دسترسی REST هر ۳۴ جدول با کلید عمومی و درخواست `HEAD` و `limit=0` بررسی شد؛
  همگی موفق بودند و هیچ ردیف داده دریافت نشد. این آزمایش بدون نشست کاربر انجام شد؛
  مجوزهای نقش کاربر واردشده در کاتالوگ دیتابیس بررسی شدند، نه با ورود به حساب کاربر.
- Security Advisor خطای دیتابیسی یا هشدار مجوز جدول نشان نداد. دو هشدار Auth
  با عنوان‌های `Leaked Password Protection Disabled` و `Insufficient MFA Options`
  وجود داشتند؛ تنظیمات Auth در این کار تغییر نکرد چون موضوع جداگانه‌ای است.

در آن بررسی اولیه هیچ دستور تغییر schema، تغییر مجوز یا نوشتن/حذف داده در تولید اجرا نشد.
این بررسی فقط کاتالوگ ساختار و مجوزها را خوانده است؛ بکاپ کامل داده‌ها نیست.

## ساخت جدول جدید

از [الگوی جدول متعلق به کاربر](templates/user-owned-table.sql) استفاده کنید.
نام و ستون‌های نمونه باید متناسب با قابلیت جدید تغییر کنند. ساخت جدول، RLS،
سیاست مالکیت با `USING` و `WITH CHECK`، و `GRANT` صریح باید در همان migration
و transaction قرار بگیرند. برنامه از Supabase Auth استفاده می‌کند و جدول‌های
شخصی جدید به مجوز `anon` نیاز ندارند. نمونهٔ عمومی ایمیل را روی همهٔ جدول‌ها اجرا نکنید.

برای جدول با UUID مجوز sequence لازم نیست. اگر جدول واقعاً sequence دارد،
فقط به sequence مربوط به همان جدول و نقش لازم، مجوز `USAGE` بدهید.

## کنترل مجوزها

[verify-data-api-access.sql](verify-data-api-access.sql) را از SQL Editor یا
MCP مجاز و فقط‌خواندنی اجرا کنید. نتیجهٔ فعلی پس از migrationها باید ۴۳ ردیف با وضعیت
`OK` باشد. این کوئری جدول مفقود، جدول جدید بررسی‌نشده، RLS غیرفعال، نبود سیاست،
مجوز جدول/schema و sequence وابسته را کنترل می‌کند. وجود سیاست به‌تنهایی
صحیح‌بودن منطق آن را اثبات نمی‌کند؛ سیاست‌های جدول تغییرکرده را جداگانه بازبینی کنید.

## محیط تازه و بازپخش schema

مخزن فعلی تاریخچهٔ کامل migrationها یا baseline کامل schema تولید را ندارد.
قطعه‌کدهای قدیمی README یا کامنت‌های TypeScript جایگزین آن نیستند.
برای پروژه/شاخهٔ تازه ابتدا schema معتبر همراه RLS و سیاست‌های موجود را بازیابی کنید.
سپس migrationهای خزانه را اجرا و در همان محیط تازه، [replay-data-api-grants.sql](replay-data-api-grants.sql)
را برای مجوزهای صریح ۴۳ جدول بررسی‌شده اجرا کنید و کوئری کنترل را دوباره اجرا کنید.
اسکریپت replay به جدول‌های مشخص و نقش‌های `authenticated` و `service_role`
محدود است و اگر جدول، RLS یا سیاستی مفقود باشد transaction کامل لغو می‌شود.
این فایل به‌تنهایی دیتابیس خالی را راه‌اندازی نمی‌کند و روی تولید اجرا نشده است.
الگو و replay در دیتابیس توسعهٔ جداگانه بازپخش نشده‌اند؛ اجرای آزمایشی آن‌ها
در تولید لازم نبود. کوئری فقط‌خواندنی کنترل دسترسی روی تولید تأیید شده است.

هر جدول جدید باید در migration خودش مجوز داشته باشد؛ فهرست کنترل و replay را
پس از بازبینی نیاز دسترسی آن به‌روز کنید. آزمایش reset فقط در محیط توسعهٔ جداگانه
با انتشار خودکار غیرفعال انجام شود. فایل‌های پوشهٔ `backups/` دستور نصب نیستند.
